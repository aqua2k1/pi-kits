# UI 项目目标

本文是 UI 项目目标的独立记录。目标不代表当前能力已经实现；
设计与实施策略见 [UI 协议与适配边界](architecture.md)。

## 核心目标

建立一组语义 UI 协议，将不同 UI 的区别与交互复杂性集中在 `shared/ui/`，
使扩展业务不依赖具体前端，能够从 TUI 逐步扩展或替换为 WebUI、GUI。

## 达成目标后的约束

1. **统一交互入口**：扩展表达业务数据与交互意图，不自行判断 TUI/WebUI/GUI。
2. **集中 UI 差异**：协议、适配器、渲染、输入、事件路由及 UI 生命周期实现
   统一归入 `shared/ui/`；前端特有依赖不泄漏到业务层。
   扩展只能消费明确的对外接口与生命周期结果，不读取宿主内部状态或拼接
   内部 signal 判断取消/错误；这些状态的归一化由共享 UI 负责。
3. **保持业务独立**：答案规则、统计计算、任务执行与业务状态归业务模块所有，
   不为切换 UI 重写这些逻辑，也不将它们迁入共享 UI。
4. **共享语义而非布局**：统一展示数据、允许的动作、结果、取消与完成语义，
   各前端自主选择布局、控件和输入方式。
5. **明确能力差异**：不支持的能力显式报告或按约定降级，不静默丢失交互。
6. **保持库边界**：共享 UI 不注册工具、命令或 Pi 生命周期处理器，
   扩展入口负责注册与宿主生命周期连接。
7. **渐进迁移**：保留现有 TUI 行为，先验证问卷与只读预览，再扩展到统计报告
   和子代理展示；新前端按实际需求实现。

## 非目标

- 不构建统一 ANSI、DOM 与 GUI 布局的万能控件 DSL 或布局引擎。
- 不要求不同前端具有完全相同的外观和操作方式。
- 不用 UI 协议解决 Herdr、执行 backend、文件系统等非 UI 宿主依赖。
- 不将后端本机打开文件或桌面通知等同于远程客户端操作。
- 不提前实现所有前端，也不重复包装 Pi 已满足需求的基础对话能力。

## 验收方向

- 同一业务用例可接入不同 UI，业务代码无需新增前端判断或改写业务规则。
- 新增或替换前端时，UI 专属改动集中在 `shared/ui/`。
- 各前端遵守相同的业务结果与交互生命周期契约。
- 取消、中止、清理、重连、会话切换和能力降级通过相应前端的实际验证。
